<b>먼저 밝혀둘 것.</b> 이 저장소는 <b>설계 명세와 단계별 검증 스크립트</b>다. 3-tier 서버가 통합 구동되는 상태가 아니다. 아래 글은 "무엇을 만들었나"보다 <b>"신뢰도를 점수로 만든다는 문제를 어떻게 쪼갰나"</b>에 대한 기록이다.
</div>

## 문제

영상 중심의 정보 소비가 급증했다. 텍스트와 달리 영상은 비정형적이고 감성적 표현이 많아서, 보는 사람이 **의심 없이 받아들인다.**

숫자가 상황을 말해준다.

<div class="tw" markdown="1">

| 지표 | 값 | 출처 |
|---|---|---|
| 유튜브 뉴스 이용률 | 전체 51%, 고연령층 55% | 정보통신정책연구원 (2025) |
| 허위·조작정보 시정요구 | 3,146건 (전년 대비 +28.7%) | 방송통신심의위원회 (2024) |
| 딥페이크·성적 합성영상 시정요구 | 6,434건 (약 4배 증가) | 방통심의위 (2024 상반기) |
| 한국인 유튜브 사용 시간 | 1,173.7억 분 (2024년 8월) | — |

</div>

취약 지점은 연령대별로 다르다. **10–20대는 정치·경제·입시 콘텐츠의 과장 및 불안 조장**에, **40대 이상은 선동형 정치 영상과 검증되지 않은 투자 유도 정보**에 취약하다.

그래서 원칙을 이렇게 잡았다.

> **정보는 자유롭게 유통하되, 그 신뢰도는 투명하게 제공되어야 한다.**

## 설계 결정 ① — 차단하지 않는다

가장 먼저 정한 건 무엇을 **하지 않을지**였다. 이 시스템은 영상을 내리지도, 숨기지도, 경고 팝업을 띄우지도 않는다. "기술적 감시나 검열이 아닌, AI 기반의 투명하고 보조적인 공공 기능"이라는 포지셔닝이다.

출력은 **높음 / 중간 / 낮음** 3단계 등급과 해석적 안내 문구다. 재생 화면 옆에 마우스를 올리면 등급·팩트 여부·출처가 뜨는 정도. 판단은 사용자가 한다.

이 결정이 시스템 전체를 좌우한다. 차단이 목표였다면 오탐이 치명적이라 정확도가 전부였겠지만, 라벨링이 목표라면 **왜 그 점수인지 설명 가능한 것**이 더 중요해진다. 그래서 단일 신뢰도 모델을 학습하는 대신 축을 네 개로 쪼갰다.

## 설계 결정 ② — 모든 영상을 분석하지 않는다

전체 유튜브를 대상으로 STT를 돌리는 건 비용상 불가능하다. 업로드된 영상만 200억 개가 넘는다.

그래서 **오락·일상 브이로그는 애초에 분석 대상에서 뺀다.** 신뢰도 판정이 의미 있는 정치·경제·입시 콘텐츠만 통과시킨다.

이 게이트키핑을 위해 만든 게 `src/tagExtract.py`다. 유튜브 페이지의 `<meta name="keywords">`를 파싱해 영상 태그를 뽑는다. 공식 API가 아니라 HTML 스크래핑이라 마크업 변경에 취약하고, 실제로 `"태그가 존재하지 않거나 추출 불가"` 분기가 이미 들어가 있다.

## 설계 결정 ③ — 네 개의 축으로 쪼갠다

신뢰도를 하나의 모델로 뽑지 않고 네 축으로 나눴다.

<div class="tw" markdown="1">

| 축 | 방법 | 모델 / 구현 |
|---|---|---|
| **감정** | 과장·불안 조장 어조 탐지 | `nlptown/bert-base-multilingual-uncased-sentiment` — 1~5 라벨에 ×20을 곱해 0~100 환산 |
| **편향** | 정치·성별·인종·종교·경제 편향 | `facebook/bart-large-mnli` zero-shot 분류 |
| **팩트** | 수치 주장 추출 후 외부 대조 | 정규식으로 `(\d+)(명\|개\|건\|%\|원\|달러)` 및 날짜 패턴 추출 |
| **메타데이터** | 채널 신뢰도, 콘텐츠 품질 | 채널 이력 기반 |

</div>

**편향에 zero-shot을 쓴 이유**는 라벨링된 한국어 편향 데이터셋이 없기 때문이다. `bart-large-mnli`에 후보 라벨(political / gender / racial / religious / economic bias)만 주면 학습 데이터 없이 분류가 된다. 대신 영상 하나당 라벨 수만큼 추론이 늘어난다 — 배치(`batch_size: 32`)와 캐싱이 설계에 먼저 들어간 이유다.

**팩트 축만 외부 세계와 대조한다.** 주장에 숫자가 있으면 공공데이터·금융 API로 검증한다. "테슬라 주식이 35% 올랐다" 같은 문장이 대상이다. 나머지 세 축은 텍스트 안에서 닫히지만, 이 축만 시스템 밖으로 나간다.

음성은 OpenAI **Whisper `large`**로 받아 적는다. `src/mp3Download.py`가 yt-dlp로 192kbps mp3를 뽑고, Colab에서 `whisper "{file}" --language Korean --model large`로 검증했다. 서버 상시 추론으로 옮기는 건 아직 미해결 구간이다.

## 설계 결정 ④ — 가중치를 손으로 정하지 않는다

네 축의 점수를 어떻게 하나로 합칠 것인가. 여기서 두 가지 안이 나왔고, 저장소에 둘 다 남아 있다.

**안 1 — 고정 가중치.** fact 40% / bias 30% / sentiment 20% / metadata 10%, 0~100 클리핑. 단순하고 즉시 동작한다.

**안 2 — 회귀로 학습.** `src/zscore.py`가 sklearn `LinearRegression`으로 같은 네 축에서 `trust_label`을 회귀하고 `w1~w4`와 절편을 출력한다. MSE도 함께 낸다.

기획 문서가 안 2를 지지한다 — *"각 변수에는 머신러닝 기반 가중치를 설정하여 계산하며, 데이터베이스가 쌓여 갈수록 정교화됩니다."* 사용자 피드백이 누적될수록 가중치가 스스로 조정되는 구조를 의도한 것이다.

다만 **`trust_label`을 누가 붙일 것인가**가 남는다. 회귀를 학습하려면 정답 신뢰도가 있어야 하는데, 그게 바로 이 시스템이 만들려는 값이다. 이 순환은 아직 풀리지 않았다.

## 실시간 설계

분석이 오래 걸리는 작업이라 결과를 기다리게 할 수 없다. 그래서 WebSocket 기반 진행률 푸시를 설계했다.

```
ws://localhost:8000/ws/ws/{client_id}
  → {"type": "subscribe_analysis"}
  ← analysis_started / analysis_progress / analysis_completed / analysis_failed
```

여기서 까다로운 지점이 하나 있다. **`client_id`별 연결과 `analysis_id`별 구독이 서로 다른 축**이다. 한 사용자가 여러 영상을 동시에 분석할 수 있고, 재연결하면 구독을 복원해야 하며, 완료된 구독은 정리해야 한다. 연결 상태 조회 엔드포인트가 세 개(`/ws/connections/status`, `/user/{id}`, `/analysis/{id}`)나 설계된 것 자체가 이 복잡도의 흔적이다.

진행률도 간단하지 않다. 모델 추론의 실제 진행률은 관측하기 어려운 값이라, 단계 기반으로 근사할 수밖에 없다 (`progress: 40, "AI 모델 분석 중..."`).

캐시는 영상 ID가 아니라 **본문 텍스트의 md5 해시**를 키로 쓴다(TTL 3600초). 같은 내용이 재업로드되면 재사용된다.

정직하게 정리하면 이렇다.

<div class="tw" markdown="1">

| 항목 | 상태 |

| 서버 3-tier 통합 | 미구현 |
| 크롬 확장 | 미구현 |

**성능·정확도 수치는 없다.** 문서의 JSON은 전부 예시값이고 측정 결과가 아니다. 모델 정확도를 재려면 라벨링된 평가셋이 필요한데, 그 라벨을 만드는 문제가 위의 `trust_label` 순환과 같은 문제다.

이 프로젝트에서 실제로 얻은 건 코드가 아니라 **문제를 네 축으로 쪼갠 분해**와, 각 축이 기술적으로 가능한지를 단계별로 확인한 검증이다.
